**Bug (Jim Stubbs, 2026-07-11):** approving an online booking texted the customer a confirmation BEFORE DJ could add tech + line items in Workiz. Root cause: `api_booking_request_approve` (routers/owner/booking_requests.py) — when the booking REUSES the customer's live re-engagement / reactivation-graveyard Workiz job (Jim had Reactivation Campaign lead 379, graveyard job 4F6ZII), it set `SubStatus: 'Send Confirmation - Text'`, which fires the Workiz confirmation-text automation immediately.

**Fix (final, commit 69cdaa2 — superseded 8947233's 'Scheduled'):** reuse path sets **NO SubStatus at all** — only JobDateTime/JobEndDateTime/JobType/type_of_service_2. DJ explicitly: "why are you flipping the status? just drop me in Workiz — I'll flip the status." So it matches the CLONE path: create/date the job, return the workiz_link + line_items (clipboard), and DJ opens Workiz, pastes items, enters tech, and flips the status HIMSELF (Scheduled → Send Confirmation). ★ Re-reuse is now guarded by **clearing the reactivation lead's `x_workiz_graveyard_uuid`** on approve (`{'stage_id':4,'x_workiz_graveyard_uuid':False}`) so a booked lead is never re-found — the old SubStatus-based guard is now just a backstop. The booking request SO is still linked + `action_confirm`ed (job shows on the Render schedule; no customer text — only `… - Text` substatuses text).

**Half-of-day preference slot filter (commit 62bcead, 2026-07-11):** the online-booking REVIEW screen (`booking_requests.html` + `api_booking_request_detail`) now only OFFERS time slots in the customer's preferred half — Morning → `minute < AM_CUTOFF_MIN`, Afternoon → `>= AM_CUTOFF_MIN` — and re-points the green "suggested" slot into that half, so DJ can't accidentally book the wrong half (DJ almost gave an afternoon-pref customer a morning time). If the preferred half is FULL it falls back to all slots + `pref_full` flag → the UI shows an amber warning + suggests picking another day; empty-slots default now uses 1:00 PM for afternoon-pref (was hardcoded 8:00 AM). The `pref` values are Morning/Afternoon/Anytime (from the booking request queue).

**Backup clone source (commit 3db6d1e, 2026-07-11):** approve's clone path required a past job of the EXACT requested `job_type` with a Workiz UUID → errored "No previous 'Combination of Services' job..." the first time a customer books a service they've never had (e.g. a combo). NOT a name mismatch — the website JOB_TYPES values (booking.py L54) ARE the real Odoo/Workiz JobType strings ('Combination of Services' etc.). Fix: if no same-type job, fall back to the customer's most recent job of ANY type. Works because SA 1338 clone sets `clone_job_type` = the requested service, so the source is only for ClientId/phone/address; DJ just fixes the line items (the clipboard preload comes from the fallback source's items, which may be a different service). Same-type still preferred first (matching items).

★ The CLONE path (non-campaign customers, `WORKIZ_CLONE_SA` = SA 1338) already created the job with NO SubStatus, so it never had this bug — only the reuse path did. ★ The reactivation "Book" flow (reactivation.py `api_reactivation_book`) also correctly sets no SubStatus. ★ Booking `/api/request` only creates a Submitted Odoo SO (no Workiz job) → review queue; the Workiz job is created/reused at APPROVE time.
