**Built 2026-08-19 (DJ-approved via Lead).** DJ can say to the field voice assistant *"text Larry about his Friday appointment"* / *"send Mrs. Johnson a text"* → Claude resolves the customer, drafts a grounded text, and drops DJ in that customer's inbox thread with the draft **prefilled**. The tool **NEVER sends** — DJ reviews/edits and taps Send himself (dialer-prefill pattern, [[feedback_call_opens_dialer_never_dials]] + draft-first [[feedback_email_draft_first_always]]).

**Three pieces (all reuse existing primitives — house style: one generic tool + good prompt):**
1. **`sms.py _draft_outbound(partner_id, intent='')`** — the drafter. Reuses the SAME `_inbox_brain()` system + `_customer_context(partner_id)` grounding as the inbox reply drafter, so it never invents a price/date/arrival-time/address (see [[project_inbox_drafter_grounding]] / [[project_inbox_drafter_invents_times]]). Framed as an OUTBOUND *initiate*, NOT a reply. ⚠️ I deliberately did NOT reuse `_draft_reply()` directly: its user prompt hardcodes *"the customer's latest text: <message>"*, so passing DJ's intent into that slot would make the model reply to DJ's own instruction. `_draft_outbound` is the correct-framing sibling. **No sign-off** in the draft — the WSC signature auto-appends at the send funnel `_send_sms` ([[project_wsc_signature_on_every_text]]).
2. **`field.py` READ tool `open_text_draft(partner_id, intent?)`** (in `READ_TOOL_MAP` + `TOOLS`). The model must resolve the customer to a `res.partner` id **via `odoo_query` FIRST**, domain including `['company_id','in',[1,False]]` (CLAUDE.md rule 8 — W&SC customers are mostly company=False), numbered picker on >1 match — spelled out in SYSTEM_PROMPT's **"Text a customer"** workflow block + HELP_TEXT. The tool reads name/phone (walks to parent person if the matched record has no phone), calls `_draft_outbound`, and returns an `<a href>` card → `/static/owner/v2_inbox.html?open=<pid>&draft=<urlencoded>`. It mirrors `navigate_to`'s early-return in `_agent_loop` (`if name in ('navigate_to','open_text_draft') and '<a href=' in result: return`), so the card is shown as the assistant's message. It is a READ tool (no confirmation), because it only drafts/opens — the actual send is a separate manual step.
3. **`v2_inbox.html` deep link `?open=<partner_id>&draft=`** → `openByPartner(pid, draft)`: resolves partner→phone via the EXISTING `/owner/api/inbox/thread_by_partner` endpoint (which **backfills a conv via `_conv_new_backfilled` so a never-texted customer still opens** — `?c=<norm>` alone returns `ok:False` for them), then reuses `openThread(norm, true)` and prefills `#reply`. Init IIFE: `?open` wins over `?c`.

**Hard company guard (added 2026-08-19 after Lead fresh-eyes, field.py e459030):** `tool_open_text_draft` re-reads the resolved partner's `company_id` and REFUSES (friendly message, no thread opened) if it's not 1 or False — the `company_id in [1,False]` prompt filter is soft, so this enforces it in code so a mis-resolved Cheryl(2)/Saunders(3) id can't slip one tap from sending. Lead's audit otherwise = SHIP AS-IS (no XSS — draft hits DOM only via `#reply.value`; quote↔URLSearchParams round-trips cleanly; READ tool only; Send bound solely to the button, no Enter-to-send).

**Resolver-level guard (added 2026-08-19, sms.py b6a6a26):** per Lead's cross-company leak-class rule (guard at the RESOLVER/chokepoint, not each caller — `company_id` FAILS OPEN since W&SC customers are mostly False), the shared chokepoint **`inbox_thread_by_partner`** (used by BOTH this voice tool AND the job-detail 💬 Texts button) now refuses any partner whose `company_id` is a truthy non-1. **Filter-then-hop v2 (sms.py 3970f1a, field.py a8fc492):** both resolvers WALK `parent_id` for the name/phone they return, so per Lead's v2 rule ("the record you CHECK must be the record you RETURN") they now RE-check `company_id in [1,False]` on the walked-to parent too — a False child can hang under a Cheryl/Saunders parent. Audit result: booking.py's public surface resolves partner_id only from HMAC-signed tokens (no unsigned `?partner_id=` door), so it's not the portal's bug class; my other partner resolvers are owner-auth. See the portal's parallel fix (portal.py `_is_wsc()` at `account()`).

**Why partner_id not norm for the deep link:** `/api/inbox/thread?c=<norm>` returns `ok:False` if no conversation exists yet; `/api/inbox/thread_by_partner?partner_id=` seeds one. So outbound-to-a-never-texted-customer works.

**Steering fix (2026-08-19, field.py 48047b5) — model wasn't CALLING the tool.** DJ tested "text Michael Krause, ask to move Friday→Thursday AM"; the quick model (Haiku, Think hard OFF) resolved Michael Krauss + wrote good drafts BUT printed them as plain text and said *"I don't have a tool to send text messages directly, but I can help you draft…"* — it never called `open_text_draft`, so DJ was never dropped into the thread. Tool was live/wired the whole time; pure steering gap. Fix = hardened the tool description ("THE way to text a customer… you MUST call this… never say you don't have a tool to send texts") + a ⛔ CRITICAL line atop the "Text a customer" workflow (MUST end by calling open_text_draft; do NOT print drafts inline). If Haiku still balks, **Think hard (Sonnet)** calls tools far more reliably — that's the fallback. Lesson: a tool existing ≠ a weak model using it; imperative "you MUST call X, do NOT do Y instead" beats descriptive.

**Agentic mandate (added 2026-08-19, field.py 7080c4b) — DJ complaint:** he said *"text Michael Krause, tell him I have an opening tomorrow morning and want to move this week's appointment"* and the voice assistant (Haiku 4.5 first pass) replied *"I don't see an active scheduled job for him… do you have a specific appointment booked? give me the SO number/date… which name should I correct?"* — i.e. it bounced the lookup work back to DJ instead of doing it. DJ: *"Claude Code would work through this and figure out to check this week's schedule and get the correct job. I need that same intellect from the voice assistant."* Fix = SYSTEM_PROMPT additions (NOT a model change — the date + a 14-day weekday→date map are already injected via `today_str`, so "this Friday" already resolves; the model just wasn't told to act):
- A top-priority **"BE AGENTIC — figure it out yourself before asking DJ"** section: try tools before asking; "I don't see a job" = search harder (widen dates, check this week/upcoming, check property children), not a question for DJ; when DJ references an existing appointment, GO FIND the SO (property children → sale.order, date_order>=today, state in sale/done) — never ask for SO#/date; never make DJ spell a name (search `name ilike` distinctive part, tolerate Krause→Krauss, use a single close match); chain steps without stopping; output `[ESCALATE]` (hands off to Sonnet 4.6) rather than dumping questions.
- The **"Text a customer"** workflow now has an explicit "if DJ referenced an existing appointment, find that job first" branch.
Model tiers: field voice `_agent_loop` runs **Haiku 4.5** first (max_loops=4), escalates to **Sonnet 4.6** only on `[ESCALATE]` or loop-exhaustion. Haiku answering with clarifying questions = an `end_turn`, so it never self-escalated — the prompt now pushes it to act or escalate. This is a general behavior standard for the voice assistant, not just the text tool.
