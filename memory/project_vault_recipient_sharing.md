The Vault is Google Drive under `VAULT_ROOT_ID = "1uVXJjg4YYfqcijh4Vbvf-snWGfUIyb9Q"` (notes.py). Sharing is per-item: a Drive file's `properties.shared_with` = comma list of recipient partner-ids, or `shared_all='1'`. Gate = `_shared_visible_to(props, vp)` = exact-id (never substring — `_shared_set` splits on comma) OR shared_all. `pinned='1'` = DJ's personal shortcut, never shown to a recipient. Recipient identity = the session `p` (partner id), taken from the authenticated session ONLY (cheryl/documents.py `_viewer_pid`), never a client param. Cheryl's view = `/cheryl/api/documents` → `owner_notes.documents_for_recipient(pid)`; open one = `/cheryl/api/documents/{id}` → `recipient_read` (re-verifies the share, default-deny).

**★ DRIVE IDENTITY (the key fact):** `_drive_service()` is a **single OAuth identity** (env GOOGLE_OAUTH_CLIENT_ID/SECRET/REFRESH_TOKEN — windowandsolarcare@gmail.com), NOT a service account. "Quick Notes" and its tree are owned by a DIFFERENT (render service) account, shared with the OAuth identity. Consequence: a **parent-scoped `Files.list` does NOT reliably return a CROSS-OWNER child** — e.g. the EIN PDF DJ uploaded directly (owned by his gmail) sitting in a service-account-owned folder. `files().get`/`get_media` BY ID still work cross-owner; a raw `'folder' in parents` BFS does not descend reliably across owner boundaries (but `notes_index`'s name-lookup path — `_find_or_create_folder` + `_get_categories` + `'cat_id' in parents` — DOES surface such a file).

**Bug + fix (2026-09-10): a shared FILE never reached the recipient; shared NOTES did.** TWO passes — the 1st FAILED QC:
- **1st pass (FAILED — do not repeat):** widened `documents_for_recipient` to BFS the whole vault (`_all_vault_folders`) + per-file `_shared_visible_to` gate. Still missed the EIN — the cross-owner file isn't returned by the OAuth identity's parent-scoped Files.list at all, and its custom `properties` aren't reliably readable to gate on. Folder-scope was NOT the real cause.
- **2nd pass (SHIPPED, index-driven):** a share is now recorded in an AUTHORITATIVE index — ir.config_parameter **`wsc.vault.shares`** = `{file_id:{"w":[recipient ids],"a":0/1}}`, written by `set_share`. `documents_for_recipient` reads the index for the recipient's file_ids and fetches **each BY ID** (`files().get`, works cross-owner) — NO folder walk. Gate helpers: `_share_index_set` / `_index_allows`. `recipient_read` + `recipient_file_bytes` gate = `_index_allows(id) OR _shared_visible_to(props)` (index authoritative; props fallback). A one-time **backfill** (`_backfill_share_index`, flag `wsc.vault.shares_backfilled`) seeds pre-index shares using notes_index's proven scan path; runs lazily on the first `/cheryl/api/documents` call. `pinned='1'` shortcuts still never shown. **Lesson: for cross-owner Drive files, record shares in OUR OWN index + fetch by id — never rely on a parent-scoped list or on reading the file's props.**
- **3rd pass (SHIPPED — the pinned trap):** with the index correct (Lead read `wsc.vault.shares` = EIN + Test Note both `{"w":["23243"]}`) the EIN STILL didn't list while Test Note did — identical index entries. Decisive tell: `recipient_read` returned **403 "not shared" (d is None), NOT a 500** → `files().get(EIN)` SUCCEEDED and the GATE rejected it; the only per-file skip left (get works, not trashed) = **`pinned='1'`**. The EIN is a pinned shortcut DJ ALSO shared; the "shortcuts never appear in a shared view" rule hid it in both the listing and the read. FIX: `_index_explicit(file_id, vp)` (exact id in index `w`, NOT shared_all) — a PINNED item that's EXPLICITLY shared to a recipient now reaches them; a pinned item with only shared_all stays private (personal shortcut never broadcasts). Applied at all 3 skip points (documents_for_recipient + recipient_read + recipient_file_bytes). **Lesson: `pinned` (shortcut) and `shared_with` are independent — a file can be both; an explicit exact-id share must override the pinned-hide.** (NB: str/int was a red herring — the index stores `w` as strings and both sides `str()`-normalize.)
- **OPEN root cause (app-share ≠ Google Drive ACL):** `recipient_read` returned a raw Drive `webViewLink` for a file — which 403s a recipient who isn't on that Drive file's Google ACL. The app-level `shared_with` does NOT grant Google Drive access. FIX: `recipient_file_bytes(viewer_pid, note_id)` (re-verifies share, default-deny) streams the raw bytes via `svc.files().get_media` (like the md1 note path); new endpoint `GET /cheryl/api/documents/{id}/raw` (cheryl/documents.py) serves them `Content-Disposition: inline`; `static/cheryl/documents.html` opens a file via that app URL, not the Drive link. **Rule: a recipient opens shared files THROUGH the app (get_media), never via a Google Drive link — the app is the UI, users never touch the backend** (see [[feedback_never_send_dj_to_odoo]]). Native Google docs (`application/vnd.google-apps.*`) aren't raw-downloadable → recipient_read serves their exported text instead.

The `/raw` endpoint is under `/cheryl`, so it's also protected by the role-isolation guard ([[project_auth_role_model_cheryl_isolation]]) — only a cheryl session reaches it. Share targets = res.partner with `x_render_role` set (≠owner), company_id in [1,False] (notes.py `share_targets`).
