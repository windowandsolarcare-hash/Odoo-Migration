**★ REUSABLE ASYNC "kick-off + poll" PATTERN (the fleet's #1 build→ship friction fix — use for ANY slow endpoint):** a batch that fires hundreds of sequential Odoo reads (here ~21 SOs × best_fit, dates spread over 6 months so per-date caching barely overlaps) is **too slow for a synchronous HTTP return** (>110s → curl times out; a local bg curl gets memory-reaped) AND a **429-storm risk to DJ's live Odoo**. Pattern: POST spawns a **daemon thread** that runs the compute once and writes `{job_id,status,dry,started_at,finished_at,result(jsonb),error}` to a **Render Postgres** table, returning `{job_id}` immediately; `GET …/status?job_id=` reads PG. **PG, NOT ir.config_parameter**, because (a) numInstances=2 — the POST thread runs on ONE instance but the status GET can hit EITHER → the handoff store must be SHARED; (b) data-location: a derived compute result is operational → Postgres (see [[feedback_data_location_odoo_vs_postgres]]). Short-lived autocommit `psycopg.connect(MEMORY_DB_URL)` conns (don't touch memory_store's shared conn); `CREATE TABLE IF NOT EXISTS` in the POST path (so a status GET before any POST 500s on the missing table — harmless, POST always precedes poll). **Run-once guard:** a still-'running' job started <15min ago is returned instead of re-firing (no duplicate storm); older 'running' = dead-instance → a new POST supersedes. Light per-SO `time.sleep(0.25)` pacing keeps Odoo under 429 (free under async). Verify async is live with the SAFE compute-free `GET /status` probe, never by POSTing the slow route against still-deployed old sync code.

**★ SCHEDULER-ENGINE ADDITIONS (LIVE on main — future scheduler edits must know these exist), both purely additive `=None` kwargs threaded best_fit_plan→rank_days→_rank_days_at→build_day_plan, None-path byte-identical:**
- **`extra_busy`** (list of `(date_str, start_min, dur_min)`): virtual reservations unioned into build_day_plan's `occupied` (same format as `held_intervals_for_day`), date-scoped. A batch re-date accumulates each computed move into extra_busy BEFORE the next best_fit → **de-pile** works identically in dry and real (dry==real; real race-proof, not relying on each write being visible via held reserves).
- **`_day_cache`** (a fresh dict per request): memoizes build_day_plan's PROPERTY-INDEPENDENT per-date baseline (day_sos + coords + held + is_day_off) so a batch does ~1 Odoo read/unique-date instead of per-candidate-day. NOTE: only helps when the batch shares dates — a 6-month-spread batch barely overlaps, so it's a 429-reducer, NOT enough alone to beat a sync timeout (that's why async was needed).
