**Why:** per-session mail/heartbeat crons die on session exit + expire after 7 days, so a silently-dead session went unnoticed. DJ wanted something ABOVE the fleet, always alive, that catches a stale/dead session and alerts him — WITHOUT Claude tokens (a Lead relay or pinging sessions both cost tokens).

**Built (2026-09-11, main.py tip ae64c4c):** `_scheduled_fleet_watchdog` on the existing AsyncIOScheduler, `add_job(..., 'cron', hour='*/3', minute=19, misfire_grace_time=600)` — runs every 3h, pure server-side, ZERO tokens. It:
- Fetches the **LIVE** `3_Documentation/SESSION_ROSTER.md` via the **GitHub Contents API** (`https://api.github.com/repos/windowandsolarcare-hash/saunders-render-app/contents/...`, header `Authorization: token <GITHUB_TOKEN>`, base64-decode `.content`) — the SAME env token dashboard.py uses for SHARED_MEMORY.
- ★ **Why GitHub API, not the on-disk file:** the deployed container's `3_Documentation/SESSION_ROSTER.md` is FROZEN at the last CODE deploy — doc commits (heartbeats re-stamp the roster constantly) are in Render's **Build-Filter Ignored Paths = `3_Documentation/**`**, so they DON'T redeploy → on-disk is always stale. Reusable rule: to read a LIVE `3_Documentation/*` file at app runtime, fetch it from GitHub, never from disk.
- Parses each `| **<Role>** | <ref> | <kind> | <Last-checked> | … |` row (split on `|`, role from `**…**` in cell[0], timestamp `YYYY-MM-DD[ HH:MM]` from cell[3] — time optional, defaults 00:00, so a date-only/malformed old row is still caught). Flags role if `now - Last-checked > _FLEET_STALE_HOURS` (=8; was 4 — raised to cut false positives, a live session may not re-stamp for hours).
- **EXCLUDES Cheryl's-cloud** (`'cheryl' in role.lower()`) — it can't self-stamp (no main write) + its ref churns, so its timestamp is never a valid staleness signal.
- **De-dupe:** ir.config_parameter **`wsc.fleet.watchdog`** = `{role: iso_when_alerted}`. Alert only on a FRESH→STALE transition (role not already in state); clear a role from state once it's fresh again so a later staleness re-alerts.

**★ RETARGETED to LEAD, not DJ (2026-09-13):** the alert was a `push_dj` card — which surfaced to DJ as a "WATCHDOG NEEDS YOU / type your answer" INPUT prompt. **Fleet health is NOT DJ's to adjudicate** (raise-the-bar rule): DJ can't `CronList`+re-arm a session's watcher. Now `_watchdog_post_lead(title, body)` **prepends a `-> Lead` entry to `3_Documentation/AGENT_MAIL.md`** via the GitHub Contents API (CAS: GET sha → PUT `entry+cur`, one retry on 409) — Lead's watcher picks it up. **Mark-on-success:** `state[role]` is set ONLY after a successful post, so a failed post retries next run (no lost alert). No DJ push at all now.
- **★ WORDING points at the real diagnostic:** a stale roster row usually means the session is **ALIVE but its watcher CRON WAS KILLED** — indistinguishable from a dead session on the roster (this is exactly what the watchdog EXISTS to catch — the 2026-09-13 Design case: alive+idle but its mail-watcher cron was killed → stamped nothing for 11h). Body: "FIRST MOVE: run CronList for that role's session and RE-ARM its watcher if empty — do NOT assume it is dead." **Do NOT weaken detection or add a "suppress if the peer is alive in ListAgents" bypass** (Lead 2026-09-13) — that would hide the real dead-watcher case (and the server-side watchdog can't see ListAgents peers anyway).

**★ DJ ESCALATION ADDED (DJ-directed 2026-09-13) — Lead-first, DJ-if-prolonged:** DJ was frustrated that Operator + Portal went silently unreachable for DAYS and he was never told (the Lead-only route fell on the floor because it alerts ONCE per episode + depends on a Lead session being awake to act). This does NOT reverse the "Lead fixes fleet health, not DJ" rule — it adds a backstop ON TOP: (1) **keep-nagging** — re-post to Lead while a role stays stale (~6h cadence, not one-shot); (2) **escalate to DJ** via the app's existing DJ-notify path only after a LONGER threshold `_FLEET_ESCALATE_HOURS`=24 (Lead had its chance, still broken → DJ needs to know he can't reach a role he uses). Escalate once per episode, clear on fresh. Brief: `3_Documentation/FLEET_WATCHDOG_ESCALATION_BRIEF.md`; handed to Specialists 2026-09-13, Lead QCs. **State shape migrates** bare-iso → `{first,last_posted,count,escalated}`.

**★ LESSON (Lead 2026-09-13): this watchdog is BUILT + LIVE — do NOT tell DJ it "was decided but never built."** A stale roster row is almost always a session that is ALIVE but whose heartbeat cron died (proven again 2026-09-13: Operator[6e9831] + Portal[ee491d] both stale for days yet both alive+idle in ListAgents; Lead reached Operator instantly via SendMessage). So when DJ asks "can I reach X," the answer is a LIVE `ListAgents` check, not the decaying roster timestamp. Render physically CANNOT stamp a session's ref for it (only the live session knows its own id) — so the heartbeat is inherently session-side (a legitimately temporary, session-scoped cron per DJ's rule); only the MONITORING is durable/server-side, which is correct and already done.
