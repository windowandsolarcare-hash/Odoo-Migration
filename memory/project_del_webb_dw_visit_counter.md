**Built 2026-10-30 (Frontdoor), LIVE 2026-10-31 (main.py commit bcc9437f; store module commit 7a2d7207).** DJ asked (via Dispatcher) whether anyone besides him had hit the Del Webb landing page via the QR code, and green-lit a real counter after we found there was NO tracking at all (no GA/pixel; only Render's rolling ~7-day access log). The EDDM postcards were **delivered Fri Oct 30 2026**, so the QR (wscare.pro/dw) only reached real recipients that day — the counter captures scans "from day one."

**How it works (server-side, the reliable capture point):**
- **Store module `routers/dw_hits_store.py`** (NEW, **Frontdoor-owned** — /dw is Frontdoor's surface). Mirrors `routers/owner/telemetry_store.py` exactly: PG-only, **fail-silent** (never raises into the request), single long-lived locked conn w/ reconnect, idempotent `CREATE TABLE IF NOT EXISTS`, **append-only INSERT** (one row per hit — deliberately NOT an `ir.config_parameter` read-modify-write, which would lose concurrent scans when the mail lands and people scan in bursts). **ZERO Odoo calls** (per [[feedback_data_location_odoo_vs_postgres]] — app operational/derived data → Render Postgres; an Odoo write here could 429 the real booking path).
- **Table `wsc_dw_hits`** on the **wsc-memory-pillar** Postgres (`dpg-danl5vqjnfac7390g8g0-a`, db `wsc_memory_pillar`, region oregon). Columns: id, ts, path, remote_ip, user_agent, referer, query_string, is_bot. DB resolution chain `DW_HITS_DB_URL→TELEMETRY_DB_URL→SMS_DB_URL→DATABASE_URL→MEMORY_DB_URL` (MEMORY_DB_URL is the one set today → lands beside the memory-pillar + telemetry tables, no collision). Schema **self-creates on first hit** (`record()→ensure_schema`), so no boot hook was added.
- **The /dw route wire (`main.py`, Specialists' file — the ONE coordinated touch):** route changed to `async def _dw_landing(request: Request)` and logs via a **post-response Starlette `BackgroundTask(dw_hits_store.record, request)`** on the `_Redirect(...)` — so the write runs AFTER the redirect is sent, in a threadpool: **zero added latency** to the visitor and it can't break the redirect. `_Redirect` is a starlette `RedirectResponse`, so `background=` is valid (Specialists confirmed, not assumed). Also added `Request` to `from fastapi import FastAPI, Request` (wasn't imported). No authz change (/dw is already `PUBLIC_ROOT_EXACT`), no new route/endpoint.
- **Bot classification** `_is_bot(ua)`: lowercased UA regex (bot|crawl|spider|applebot|facebookexternalhit|preview|headless|python-requests|curl|wget|…) + **empty UA = bot**. Verified: Applebot/facebook/empty→bot; real iPhone/Android browser UAs→human.

**How to READ the running count (no endpoint — read the table directly):** Render MCP `query_render_postgres` on `postgresId dpg-danl5vqjnfac7390g8g0-a` (select workspace `tea-d78l9fqdbo4c7388n9og` first — session state resets between MCP calls). Headline query: `SELECT count(*) hits, count(*) FILTER (WHERE is_bot) bots, count(*) FILTER (WHERE NOT is_bot) humans, count(DISTINCT remote_ip) uniq_ip FROM wsc_dw_hits;`. The module also exposes `stats(since_hours=None)` (headline + per-day Pacific human/bot + recent rows) if an in-app endpoint is ever added. DJ watches only **Dispatcher** — route count updates through Dispatcher, plain-English ("real people vs bots", not jargon). **★ `query_render_postgres` is READ-ONLY** (a DELETE/UPDATE through it errors `cannot execute ... in a read-only transaction`, SQLSTATE 25006) — so you can COUNT/SELECT but can't prune test rows via the MCP; a real write would need the live DB creds (don't fetch secrets for cosmetic cleanup). Always report the **non-bot** count (`WHERE NOT is_bot`) so leftover bot/test rows never inflate DJ's number.

**TWO honest limitations (always state these to DJ):**
1. **Can't split QR-scan vs typed URL.** Every postcard shows the same bare URL and the cards are already printed, so there's no per-source tag. QR scanners AND typed URLs both arrive with an empty referer. BUT /dw isn't linked/indexed anywhere public — the only way anyone learns it is the card — so **real human hits ≈ card/QR response.** (A future campaign could tag the QR, e.g. /dw?s=qr; `query_string` is already stored for that.)
2. **Can't perfectly isolate DJ.** `_OWNER_IPS = {'76.90.35.160'}` breaks out "looks like DJ" — but **76.90.35.160 is DJ's local network, which is ALSO where the local fleet Claude sessions curl from** (discovered 2026-10-31: this session's own verify curl came from that IP). So owner_ip_hits conflates DJ + fleet test hits — all bot-classified anyway, so they stay out of the human count. And DJ scanning from his phone in the field comes from a cell-carrier IP, which this can't flag. So report human/bot honestly and treat the owner-IP number as "DJ/fleet testing, approx," never an exact DJ count.
