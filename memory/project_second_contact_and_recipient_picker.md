**Second contact (spouse) per customer — DJ 2026-08-21.** Two char fields on the **PERSON** res.partner (parent of the property, per [[project_so_partner_id_is_property]]): **`x_studio_secondary_phone`** (id 21390) + **`x_studio_secondary_name`** (id 21393). Primary stays the existing `phone`; its label = the person's first name. Lead creates the fields/data.

**"Who to text" recipient picker — lives in `_openSendBox` (v2_field.html).** The shared field composer takes **`opts.recipients`** = `[{name, phone, which:'primary'|'secondary'}]` and renders a radio row ("Send to: ⦿ Nancy — primary / ○ David — 2nd") above the editable message, **default = primary**. DJ's rule: **ALWAYS show the row even for a single number** (guard is `_recips.length>=1`, NOT `>1`) so he confirms the right person. `onSend(msg, chosen)` receives the chosen recipient; each caller passes `chosen.phone` to its send endpoint.
- **Wired so far (2026-08-21):** the **Zelle request** (`/owner/api/job/zelle_request`, `specialist_billing.py`). Its preview returns `recipients` (primary off person phone/first name + secondary off the two fields); send honors a **`to` override VALIDATED against the known numbers only** (never texts an arbitrary/injected number); idem keyed `zelle:<so_id>:<dest>` so sending to the spouse isn't deduped against a primary send.
- **Still TODO (Stage 2):** extend to the other button-texts. `_openSendBox` is already the home; each needs `opts.recipients` passed + a `to` override on its endpoint. Endpoint phone handling: **stripe `/api/stripe/send_sms` already takes `phone`**; **eta `/api/eta`, photos `/api/job/photos_send`, zelle** resolve server-side and need a `to`/recipient override added (`messaging.send(to=…)` already accepts any destination).

**`_openSendBox` now also does 📧 Email + 📤 Text as equal choices (2026-08-21).** Added optional **`opts.onEmail`** (async, returns `{ok,email?}`), **`opts.emailLabel`**, **`opts.emailOkMsg`**, **`opts.noText`** (hide the text-send button → email-only) to the shared composer — **purely additive**, flows without `onEmail` are unchanged. When `onEmail` is set it renders 📧 Email + 📤 Send as EQUAL primary buttons and "Don't send" drops to a full-width row. The send-button handler is now null-guarded (can be absent under `noText`). **First wired:** the **Stripe pay-link send** (`doStripeLink`, v2_field.html, commit 816e46d) — Email reuses the existing **`/owner/api/stripe/send_email`** (no new sender), Text reuses `send_sms`; **no phone → Email-only**, no phone+no email → link created, use Charge at Door. Was DJ's Angela case (online desktop payer, text-only before). **Folding invoice-send (`fdInvOpen`) + Zelle into the same Email+Text picker is now ~3 lines each** — offered to Lead, not yet done.

**`_openSendBox` gained `opts.onCancel` + the Stripe "stuck greyed button" fix (2026-08-21, commit 6adfe4c).** `opts.onCancel` fires when the composer is dismissed WITHOUT sending (backdrop tap or "Don't send") and NEVER after a real send/email (guarded by an internal `_obDone` flag set in the send + email success paths). **Bug it fixed:** after generating a Stripe link, `_showStripeWaitUI` hard-disabled the shared `pay-btn` to a dead "Waiting…", and the only reset ("✕ I Didn't Pay") lived in the volatile `#field-status` — so abandoning the send never reset it, and the `sp_<so_id>` localStorage flag re-latched the disabled button on every job reopen (Rule 12/13). Fixes: (1) the waiting button is now **tappable "Resend Stripe Link"** (enabled) and **force-selects the Stripe method** (`preselectPayMethod('stripe')`) so tapping always regenerates the link instead of misfiring a Record Payment on resume; (2) `doStripeLink` passes `onCancel:_cancelStripeWait` so backing out clears poll + `sp_` pending + re-enables; (3) `_cancelStripeWait` restores the correct label under the Stripe method. Stuck jobs self-heal on reload (`_resumeStripeIfPending` → tappable Resend, not greyed). ★ The single `pay-btn` is shared between "Record Payment" and "Send/Resend Stripe Link" — set by `pickMethod`/`payMethod`; any change to its disabled/label state must respect the selected method.

**★ Edit PERSON-level customer fields from ANY job = the field "Full details" editor.** Read = **`/owner/api/so_full`** (dashboard.py) builds the "Customer" group; Write = **`/owner/api/brain/job` `brain_job_save`** (brain.py) via synthetic `cust_*` keys. Three write maps: `_CUST_BOTH` (street/city/zip/phone → property AND person), `_CUST_PROP` (gate/pricing/frequency/type/service_area → property), **`_CUST_PERSON`** (`cust_secondary_phone`/`cust_secondary_name` → **person only**, added 2026-08-21). The frontend details editor (`v2_field.html` `loadFullDetails`/`saveFullDetails`) is **generic** — it renders whatever fields so_full returns and posts any changed `[data-key]` — so exposing a new field is backend-only (add it to so_full's group + a brain_job map). This is the canonical "edit the customer without opening Odoo" path.
