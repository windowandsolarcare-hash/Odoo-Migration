**★ CORRECTION 2026-10-24 (Specialists firsthand, Lead concurred) — the earlier "APScheduler tick blocks the loop → fix = run_in_executor" attribution was WRONG:**
- `build_scheduler()` uses `AsyncIOScheduler` (main.py:774); every `_scheduled_*` is a plain sync `def`, `_sched_singleton` returns a sync `wrapped()` (main.py:724). APScheduler's default **AsyncIOExecutor runs non-coroutine jobs via `loop.run_in_executor(None,…)`** → the jobs ALREADY run in a thread, off the loop. **So wrapping them in run_in_executor again = a NO-OP** ("green deploy ≠ fixed"). The minute-boundary correlation was a red herring (scheduler logs print every minute).
- `/healthz` is `async def` + pure in-memory (main.py:1025-1034, "FAST — no live Odoo call"). A 5s timeout = the **event-loop thread frozen >5s**. Metrics at the failures: CPU flat **≤0.16 core**, mem **≤77%** of 512 MiB → NOT CPU/GIL/OOM. A frozen loop with low CPU = a synchronous blocking I/O call on the loop (blocked on a socket).

**★ PINNED CULPRIT (Lead-approved trace, 2026-10-24):** `api_owntracks_webhook` — `async def`, `POST /owner/api/owntracks/webhook` (dashboard.py:13487). On **every** ping from DJ's phone (24/7), BEFORE the 2026-09-25 throttle + BackgroundTasks offload, it runs `_owntracks_resolve_emp(tid)` (dashboard.py:165-167) → `odoo_rpc('ir.config_parameter','get_param',…)` which is dashboard.py's OWN **sync `httpx.post(timeout=20)`**, un-awaited, un-threadpooled. When Odoo has a slow/429 moment that `httpx.post` stalls up to 20s → the single uvicorn loop freezes → async `/healthz` misses the 5s probe with low CPU. The 09-25 fix offloaded the HEAVY location work but left this resolve on the loop for every ping. This is the overnight-flap manifestation of the SAME class as [[project_render_502_event_loop_freeze_blocking_odoo]] (Audit 2026-10-16: dashboard.py **69 async / 625 odoo_rpc / 0 run_in_threadpool** — trace re-confirmed exactly).
