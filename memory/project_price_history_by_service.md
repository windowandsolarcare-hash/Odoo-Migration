**Feature (2026-08-20, DJ request via Lead):** a per-customer view that pivots line-item history **BY SERVICE TYPE** (product) instead of by job — DJ uses it to price a new job from past charges ("what have I charged this customer for windows / pressure washing over the years").

**Where it lives:**
- **Endpoint:** `GET /owner/api/brain/price_by_service?partner_id=` in **`routers/owner/brain.py`** (mounted at prefix `/owner`, main.py:275). Returns `{ok, customer, services:[{product_id, service, count, last, last_price, lines:[{date, raw, price, unit, qty, desc, so_name, status}]}], total_lines}`. Groups sorted most-recently-used first; lines within a group most-recent-first.
- **Page:** `static/owner/price_by_service.html` (standalone, `?partner_id=&name=`), served no-store via `html_nostore` at `GET /owner/price-by-service`. Collapsed one-row-per-service; tap expands to DATE·PRICE·DESCRIPTION rows (product name dropped in rows — it's the group header; description is the prominent field). Sunlight-readable, large-text, dark-blue brand.
- **Entry point:** 💵 Prices button in the Customer Brain customer-detail action row (`v2_customers.html` `renderDossier`, `openPrices(i)`).

**★ REUSABLE FACT — resolve a customer's WHOLE HOUSEHOLD, not just their contact id:** W&SC SOs link to the **PROPERTY CHILD** partner, not the top contact — so `sale.order` filtered by a naive `partner_id = <contact>` returns **0**. Correct pattern: read the contact's `commercial_partner_id` (the household root), then `res.partner search [['id','child_of', root]]` to get every household member (contact + property children), then filter lines by `['order_id.partner_id','in', house]`. Same reason the voice assistant is told to "check the customer's property children." Always pair with `company_id in [1, False]` (W&SC customers are mostly `False`, see CLAUDE.md rule 8).

**Line query:** `sale.order.line search_read [['order_id.partner_id','in',house], ['display_type','=',False], ['product_id','!=',False], ['order_id.company_id','in',[1,False]]]` fields `product_id,name,price_unit,price_subtotal,product_uom_qty,order_id`. PRICE shown = `price_subtotal` (actual line charge); unit rate = `price_unit`. **`date_order` is NOT on the line** — batch-read the SOs (`order_id` ids) for `date_order` + `x_studio_x_studio_workiz_status`. Skip DJ's soft-deletes (`price_subtotal<=0 AND qty<=0`).

**★ DEPLOY-ORDERING GOTCHA (hit 2026-08-20):** a new page route that does `open('static/...new.html')` and the new file itself must land in the SAME or an EARLIER commit than the route — NOT a later one. I pushed `brain.py` (the route) first, then `price_by_service.html` seconds later, so Render deployed the route-only commit first → that instance had the route but not the file → `FileNotFoundError` → **HTTP 500 during the rollout window** (some instances 200, some 500). It self-healed once the file-commit went live, but it's avoidable: push the static file BEFORE (or with) the code that reads it. (Signature was confusing — a 500 whose body was the full correct HTML — because two instances at different commits answered different curls.)

**★ `x_line_desc` is shown in THREE UI spots (2026-08-20):** (1) the 💵 by-service Prices screen (this file), (2) the **field job-detail Record Payment card** — backend reads `_order_lines_by_so` (dashboard.py ~7440, the schedule/payment list) + `api_so_history` (dashboard.py ~4815, single-job reopen) both emit a `desc` key; rendered as a dim `.pay-line-desc` sub-line under the line name in **BOTH `v2_field.html` AND `field.html`** (openJob + _repaintActiveLines twins), and (3) **Customer Brain → Job History** — `brain_job` (brain.py) section "Services / Line Items" emits `desc`; `report_kit.js openBrainFull` (~L213) renders it as a dim sub-line. **★ TITLE RULE: never show raw `name` — use `name.split('\n')[0]`.** Some legacy line names have the description baked in after a `\n` (the mess the x_line_desc split avoids); the title is always the first line, the description always `x_line_desc`. Empty x_line_desc → render nothing.

**★ DESCRIPTION field = `sale.order.line.x_line_desc` (text, field id 21381), NOT `name`.** Line descriptions were dropped in the Workiz migration; Lead backfills them from the Workiz export (`4_Reference_Data/Workiz_Final_Export_2026-08-02/...json`, matched SerialId↔SO name) into a **separate custom field `x_line_desc`** — deliberately NOT merged into `name`, because DJ needs `name` to stay the clean service label (else it breaks the by-service grouping + his sort/find). So: **group by `product_id`/`name` (the service header); read `x_line_desc` for the per-line DESCRIPTION** (the prominent expanded-row field). Endpoint reads `x_line_desc` as of brain.py 9e14ea6. Empty `x_line_desc` (not-yet-backfilled) → row shows date+price only.
