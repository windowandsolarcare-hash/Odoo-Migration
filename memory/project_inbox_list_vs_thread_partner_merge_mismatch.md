**★ RESOLUTION FIRST — do NOT read this as a confirmed bug firing.** The incident that triggered the investigation — DJ's "I left my pole at your house…" text showing under **Bill Zwick** instead of **Jeff** — was a **WRONG-RECIPIENT HUMAN SEND, not a code bug.** Operator's live read (Lead had Operator read the live SMS store app-side; it is session-unreachable, see below) showed: conv `5152493840` is **correctly Bill's** (partner **27310**), 5152493840 is **Bill's OWN Odoo number**, and the pole message **sits cleanly in Bill's thread (present, not missing).** **Jeff is a separate contact 26931 on 6127029988.** So DJ just texted Bill meaning Jeff → Jeff did NOT get it (needs a resend to 6127029988). The "missing from Bill's opened thread" did NOT reproduce live → at most a transient display artifact; **NO fix shipped (no repro).** The live-read gate worked — it stopped us staging a guard for a non-bug.
**Two lessons:** (1) a session-UNREACHABLE live store (SMS_DB_URL = momscare-db, empty IP allowlist) means a code-only root-cause can rest on a FALSE premise — confirm against the live record (Operator app-side) BEFORE staging a customer-facing fix. (2) My send-ledger inference "5152493840 = the active thread = Jeff" was WRONG: the active 4-reply thread was BILL's; `wsc_msg_sent` gives the destination NUMBER + Twilio sid/status, but NOT whose contact that number is.

**The mechanism below is a REAL but SEPARATE latent fragility (it did NOT cause this incident). Harden only if DJ wants, staged + QC'd on its own merits — NEVER rushed off an incident; watch the regression caveat (don't break a human-set link or the unknown-number standalone case).**

**Hypothetical symptom it WOULD produce (e.g. the shared-number duplicate-contact case — Sally Walsh, partners 24158 vs 23036 on one number):** a text PREVIEWS under customer A's row in the LIST but is ABSENT when A's thread is opened, and absent from the real recipient B too.

**Mechanism (code-proven):** the inbox conversation store (`sms_conversations`, DAL `sms_store.py`) is **keyed solely by `norm` = last-10-digit phone** (`_norm`, sms.py:89). `partner_id` is a PROMOTED, non-authoritative, flip-able attribute on the row. The **two-path inconsistency**:
- **LIST** (`inbox_list`, sms.py:2511) collapses rows sharing `partner_id>0` into one representative row **by the conv's STORED `partner_id`** (sms.py:2591-2604). A conv whose stored partner_id = 27310 folds under "Bill Zwick" and, if it owns the newest message, supplies the preview.
- **OPEN** (`/api/inbox/thread_by_partner` → `_merge_partner_thread`, sms.py:2763 → `_partner_norms`, sms.py:2680) re-derives the member convs from that partner's **ODOO phone numbers** (`phone` + `x_studio_x_studio_second_phone`, partner + parent).

So when a conversation carries a `partner_id` that does **not** correspond to any of that partner's real Odoo numbers, the LIST shows it under that partner but OPEN excludes it (it loads only the Odoo-number threads) → the message "appears then vanishes." The real recipient's row disappears because their conv is wearing the other partner's id/name.

**How a conv gets the wrong partner_id (two candidate triggers — not yet disambiguated; needs a live read):**
(a) **Outbound stamped a stale partner_id:** `messaging.send(partner_id=…)` writes partner_id only in `_conv_new` (messaging.py:667-689); `_conv_append` never re-stamps. A caller passing a stale/wrong partner_id (e.g. 27310, just created from the call) while `to` = a different number creates `_conv_new(norm=other#, name=Bill, partner_id=27310)`. The Twilio send still goes to `to`, so **the text reaches the right phone; only the in-app label is wrong.**
(b) **Inbound resolve-flip on a shared number:** `_resolve_partner_by_phone` (sms.py:719) returns `hits[0]` — arbitrary when ≥2 W&SC partners share a number — and the inbound path (sms.py:1976) OVERWRITES `conv['partner_id']` with it. Documented dup-on-number hazard already in code (`clear_needs_reply_for_so`, sms.py:2711: Sally Walsh, partners 24158 vs 23036 on one number).

**Delivery vs label are independent:** the number a text is SENT to (`to`/`conv.phone`) is separate from the displayed partner name. A wrong partner label does NOT by itself mean the SMS went to the wrong phone. Record of truth for the actual destination number = Twilio's sent-log (or the live conv's `phone`).

**★ LIVE SMS STORE IS SESSION-UNREACHABLE (by design):** the live inbox runs on **`momscare-db`** (`SMS_DB_URL`, Postgres id `dpg-daocj0btqb8s73eq8kt0-a`) whose **IP allowlist is EMPTY** → `query_render_postgres` returns "blocks all external connections" (a security boundary — do NOT open it; see [[feedback_cant_headlessly_seed_is_security_feature]]). The **`wsc-memory-pillar`** copy (`dpg-danl5vqjnfac7390g8g0-a`, which `MEMORY_DB_URL`/`_MEM_DB_URL` uses for the idempotency ledger) still HAS a `sms_conversations` table but it is **frozen at 2026-09-21** (the cutover date to momscare) — a stale mirror, not the live inbox. To read the live conv, go through the APP's own endpoints (the Render process holds the creds) via **Operator**, not a direct PG connection.

**Candidate HARDENING (NOT shipped — stood down for this incident; Lead parked it as a separate non-urgent item, build only on DJ's say-so + full QC):** (1) guard the stamp — only set/keep a conv's `partner_id` when that partner's Odoo number matches the conv `norm`, and on `_resolve_partners_by_phone` AMBIGUITY (≥2 partners share the number) keep the existing link rather than arbitrary `hits[0]`; (2) the LIST/OPEN consistency fix is SECONDARY/defensive only — alone it just makes a wrong grouping consistent in both views, so it must never be the primary. Regression caveat (must hold either way): never override a HUMAN-set link, and never break the new-customer-from-unknown-number case (unstamped standalone is correct).
