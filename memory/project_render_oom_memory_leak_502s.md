**Incident (2026-11-05 AM, DJ frustrated, live-ops via Dispatcher):** intermittent **502 Bad Gateway** across the whole app, "several times this morning," while Render dashboard "looks up." Mechanism #2 (the leak/OOM) traced to a **slow memory leak** pressing the **512MB per-instance ceiling** (Render **Starter** plan, `srv-d78le0fkijhs738dsli0`, 2 instances, Oregon, **single uvicorn worker each** — start cmd `uvicorn main:app` has NO `--workers`).

**Why 502 + "looks up":** when an instance's RSS crosses 512MB Render **OOM-kills** it and restarts; during the restart there's a few-second window with no healthy instance on that route → **502**. Self-heals in seconds, so a dashboard glance between blips shows healthy. DJ was also viewing only ONE of the 2 instances.

**Evidence (Render metrics, memory_usage, per-instance sawtooth — this is PROOF not theory):**
- instance `mdss8`: climbed 434→**490MB** over 14h on 11-04, then **475→206 at 20:48 UTC** = the OOM kill (event `server_failed` reason `oomKilled memoryLimit 512Mi`, 20:49). 20:48 UTC = ~12:48 PM Pacific.
- Every instance boots ~**150MB** and climbs to **360–490MB over ~1–2 days** (~+5–30MB/hr, front-loaded in first hours). Growth tracks **work handled** (one instance plateaus ~385, another climbs to 490) → a per-request / per-scheduler accumulator, not pure uptime.

- ⚠ The specific 8:06 AM Pacific burst DJ screenshotted = **BOTH** instances a **clean simultaneous graceful restart** (SIGTERM "Shutting down"→"Waiting for connections to close", then fresh boot) with **NO deploy/OOM/health event** in Render's log → reads as a **Render host event or a manual "Restart service,"** NOT an app crash. Don't code-chase this one (Lead). If anyone clicked Restart to "fix" the 502s, that click itself caused that burst.

**CONFIRMED unbounded accumulator #1 — `routers/owner/swr.py`:** module-level `_CACHE` and `_LASTGOOD` dicts, **never evicted, no cap/LRU**. `bust()`/`bust_prefix()` only pop `_CACHE`, NEVER `_LASTGOOD`. Keys include **param-keyed, non-enumerable** `calendar_jobs:%s:%s:%s:%s` (year/month/start/end, dashboard.py:10922) and `scheduled_sos:%d` (day offset) + `whoami:<code>` (bounded) + `dashboard` (1). So `_LASTGOOD['calendar_jobs:*']` grows one full-month-payload entry per distinct calendar view ever requested since boot and never clears. Real leak, though likely only PART of the ~340MB — more accumulators still to find (scheduler/prewarm baseline + other module-globals next). **First surgical fix (Lead-approved 2026-11-05, build+stage for byte-QC, ship as an independent increment):** bound `_CACHE`/`_LASTGOOD` with a **count-based LRU** (leaf helper, low blast radius, removes no working logic). Lead's 3 design constraints: (1) a COUNT cap is the deterministic guard — a TTL alone won't cap a burst (TTL ok as a secondary ager); (2) `_LASTGOOD` cap must be **≥** `_CACHE` cap so an ACTIVE key's stale-on-failure fallback is never evicted while it's still served fresh (evicting `_LASTGOOD` for a COLD key is fine); (3) size N with headroom above the concurrent calendar working-set (distinct month-views in play — dozens, not thousands). VERIFY: a slow leak won't prove fixed at boot — after QC+deploy, confirm clean boot on both instances then WATCH the Render memory trend 1–2 days to confirm the sawtooth ceiling drops (feedback_no_conclusion_from_single_test_sporadic).
