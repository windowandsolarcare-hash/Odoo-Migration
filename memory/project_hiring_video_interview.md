Built 2026-06-17. The video-interview round of the hiring ATS (`routers/owner/hiring.py` + `static/owner/hiring.html`). DJ runs it live during a Zoom/Meet call.

**Stage model (verified):** Odoo `hr.recruitment.stage`: 1 New, 2 Qualification, 3 First Interview, 4 Second Interview, 5 Contract Proposal, 6 Contract Signed. The app's STAGE_LABELS overlay: 1=Reviewing, 2=Phone Screen, **3=Interview**, 5=Offer, 6=Hired. So "phone-screened" candidates sit in Odoo stage 2; **video round = move them to stage 3** (shows under the app's "Interview" tab). Did this for David Osuna (109), Reginald Martin (156), Leonardo Garcia (151) — the 3 DJ chose (Diego Amaya 145 was NOT chosen).

**KEY DESIGN — separate store, NOT applicant_notes:** video data lives in a dedicated custom field **`x_video_interview`** (id 20877, ttype text/JSON) on hr.applicant. Why: `serializeNotes()` in hiring.html threads applicant_notes through ~10 call sites (setDecision, setDjDecision, saveEditedResume, etc.); hooking video into it risks an unrelated save silently WIPING video data. The separate field can't be clobbered. **Apply this pattern for any future per-candidate data block.**

**Data shape:** `x_video_interview` JSON = `{"general":{vq_id:{c:bool,n:str}}, "individual":[{q:str,n:str,c:bool}], "decision":"yes|maybe|no|", "date":"YYYY-MM-DD", "time":"3:00 PM", "status":"invited|confirmed|done|declined|noshow"}`. Shared core questions = param **`hiring.video.general_questions`** = `[{id,text}]` (parallels phone's `hiring.phone.general_questions`).

**Date/time/status (added 2026-06-17):** same concept/format as the PHONE Interview box (`renderInterviewBox`, `INTV_STATUSES` invited/confirmed/done/declined/noshow). Rendered in the Video section as `#vidIntvBox` (date input + time text + status chips) via `renderVideoIntvBox()`; `setVideoStatus`/`setVideoField` write into `_videoData` → saveVideo. NOTE the phone tracker uses a separate param `hiring.interviews` (the generic "Interview" box); the VIDEO date/time lives in `x_video_interview` instead (so phone + video are independent). The **📞 Interviews agenda tab now shows BOTH** — `buildScheduleHTML` merges phone (`INTERVIEWS`, 📞 icon) + video (`VIDEO_INTERVIEWS`, 🎥 icon), one day-grouped list. Bulk video data via `GET /api/hiring/video_interviews` → `{id:{date,time,status}}` (loaded into `VIDEO_INTERVIEWS` global at loadApplicants); `setVideoField`/`setVideoStatus` also `_syncVideoAgenda()` so edits show without reload.

**Seeded interviews (from Indeed emails, 2026-06-17):** David Osuna 109 = Thu Jun 18 2026, 3:00 PM, confirmed; Reginald Martin 156 = Thu Jun 18 2026, 3:30 PM, confirmed; Leonardo Garcia 151 = invited (awaiting his slot pick — DJ offered Friday afternoon). Indeed interview emails come from `no-reply@indeed.com`, subject `Confirmed: Interview with <name>` / `Interview request sent to <name>`; the **date + time are in the email body/plaintextBody** ("Thursday, June 18, 2026" / "3:00 PM - 3:30 PM PDT"), not the snippet — must open the thread (FULL_CONTENT) to read them. "Awaiting candidate confirmation" emails have no time yet.

**Reorder questions (added 2026-06-18):** both video question lists have ▲▼ up/down move buttons per row — shared **Core** (`_moveVq(id,dir)` → swap in `_videoQuestions` → `saveVideoQuestions()` PUT param, reorders for ALL candidates) and **per-candidate** (`_moveVi(i,dir)` → swap in `_videoData.individual` → `saveVideo()`). Both call `_gatherVideo()` BEFORE swapping (reads live checkbox/notes from DOM into state) so in-progress notes aren't lost, then `renderVideo()`. First-row ▲ / last-row ▼ render `disabled` (opacity .25). Up/down chosen over drag (reliable on phone, short lists). Same pattern is reusable for the phone-question lists if ever wanted.

**Collapsible sections (added 2026-06-18):** the candidate detail had too much on screen during a live interview. Every `.section-title` (AI Assessment, Evaluation, General Notes, 🎥 Video Interview, Phone Interview, Screening Answers) is now a TAP-TO-COLLAPSE header — caret ▾/▸ via CSS `::before`. Generic mechanism `_hsSetCollapsed(titleEl,collapsed)` hides the title's FOLLOWING SIBLINGS within its own parent up to the next `.section-title` (so it works for top-level titles AND the "AI Assessment" title nested in `#detailAiSection`, with NO HTML restructure). Stores each hidden child's prior `style.display` in `dataset._hsPrev` so inner toggles (vqToggle/piToggle etc.) restore correctly on expand. Collapsed set persisted in **localStorage `hiring_collapsed_sections`** keyed by title text → survives refresh AND applies to every candidate (DJ wants the same simplified view each interview). `_applyCollapsibles()` wires click handlers (once, `_hsWired`) + applies saved state; called at end of `openDetail`. Section-title elements are STATIC HTML (not re-rendered per candidate), so wiring once is safe.

**Endpoints (hiring.py):** `GET/PUT /api/hiring/video_questions` (shared core), `GET/POST /api/hiring/applicant/{id}/video` (per-candidate). All thin wrappers over the param/field.

**Frontend (hiring.html):** 🎥 Video Interview section in candidate detail, ABOVE Phone Interview. Yes/Maybe/No decision row (reuses `.dec-btn`), Core Questions list (`#vqList`, shared) + per-candidate list (`#viList`), each row = checkbox + question + notes textarea (reuses `.pi-item`/`.pi-question-row`/`.pi-notes`/`.pi-icon-btn`). Globals `_videoQuestions`/`_videoData`; `loadVideoForCandidate(id)` called from openDetail; `saveVideo()` debounced 600ms → POST. Add/edit/delete via `prompt()`/`confirm()` (core → PUT param for all; individual → saveVideo for that candidate). Did NOT touch any phone-interview function.

**Questions philosophy (DJ's rule):** before drafting, READ each candidate's actual phone-screen answers (PHONE_INTERVIEW + INDIVIDUAL_QUESTIONS in applicant_notes, mapped via the general_questions param) and DON'T re-ask what's answered. The phone screen here was thorough (covered transport/license, heights, heat, physical, attendance, pay, availability, broken-item-at-client scenario, etc.). Video round was built to go DEEPER / fill gaps (longevity/trajectory, lead/initiative, and per-candidate thin spots). Also: make questions OPEN-ENDED ("tell me about a time…", "walk me through…") because candidates give short answers; keep only factual gates (license, work-auth) closed — and skip those if already answered (Leonardo already confirmed work auth on the phone).
