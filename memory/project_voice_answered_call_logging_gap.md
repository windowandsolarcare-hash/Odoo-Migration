Found 2026-08-11 (DJ: "Sylvia called ~6pm, why isn't her call logged"). Voice = Twilio, in routers/owner/voice.py (live repo only — LOCAL Saunders Render App copy has NO voice code, it's stale).

**Root cause — answered calls could log nowhere.** `/voice/recording-saved` (answered call recording, both dirs) and `/voice/transcript-ready` only appended to the inbox thread `if conv is not None` — they NEVER created a thread — and to Odoo only `if pid`. So an answered call from a number that (a) isn't matched to an Odoo customer AND (b) has no pre-existing text thread fell through BOTH gates and logged nowhere visible. Voicemails don't have this bug — `/voice/recording-done` uses `_conv_get(norm) or _conv_new(...)`.

Sylvia's case: she called from 951-223-0263, but her Odoo record (Sylvia Zack, partner 23621) had phone 951-312-6988 only → unmatched → not logged. The recording itself DID exist on Twilio the whole time (just unattached).

**Fixes shipped 2026-08-11:**
- **voice.py** (both handlers): `existing=_conv_get(norm); conv = existing or _conv_new(norm, phone, name, pid)`; if `not existing` mark `status='open', unread=False` (answered call = logged history, NOT a false action item); `_conv_set(norm,conv); _touch(norm)`. Mirrors the voicemail path.
- **voice.py** new read-only diagnostic: `GET /owner/voice/recordings?token=CRON_SECRET&limit=N` → recent Twilio recordings (sid/call_sid/start/duration + `/owner/voice/rec?sid=` listen link). `&transcribe=<rec_sid>&phone=<caller>` re-kicks Voice Intelligence for one recording (stores `wsc.voice.trans.<tsid>` = {phone,dir}). Sibling of `/voice/recent` (which lists Twilio CALLS).
- **sms.py** `_find_customer`: now matches `phone` OR `x_studio_x_studio_second_phone` (last-7 `ilike`), so a customer calling/texting from a 2nd number is recognized. (res.partner here has NO `mobile` field — "Second Phone" `x_studio_x_studio_second_phone` is the custom secondary-number field; stored as pure digits so the suffix ilike matches.)
- Set Sylvia Zack (23621) Second Phone = 9512230263.

**Voice Intelligence transcripts — WHY they never worked (ROOT-CAUSED + FIXED 2026-08-11).** `wsc.voice.vi_service` IS set (GAe3e7587849d0c1c5b8d79fcfd1b4b75b), but every `POST {_INTEL}/Transcripts` was MALFORMED: code sent `Channel=json.dumps({'source_sid': rec_sid})`. Twilio VI requires the source_sid nested under `media_properties`: **`Channel={"media_properties":{"source_sid":"RE..."},"participants":[]}`**. Wrong shape → Twilio returned an error body with no `sid` → 0 transcripts ever, silently (the except swallowed it). FIX: both VI POSTs in voice.py (recording-saved + the /voice/recordings `?transcribe=` path) now send the `media_properties` wrapper. Verified live 2026-08-11: Sylvia's 2 calls → transcript_sids GTaba2ec…/GT78b17b…, VI auto-detected Agent(+19519278680)/Customer(+19512230263). VI is async → the service's WebhookUrl (`/owner/voice/transcript-ready`, set by `/voice/vi-setup`) fires when done → fetches `/Transcripts/{tsid}/Sentences` → saves "📄 Incoming call transcript:" to the caller's Odoo chatter + inbox thread. `/voice/recordings?...&transcribe=<sid>&phone=<caller>` now returns `vi_raw` for debugging. Voicemail transcripts are a SEPARATE Twilio `<Record transcribe="true">` path (`/voice/transcription`).

**Speaker labels wrong on INBOUND transcripts (all lands as one speaker) — cause + fix (2026-08-11).** transcript-ready maps `spk = 'Customer' if str(media_channel)=='1' else 'Dan'` — i.e. it separates speakers BY CHANNEL. But INBOUND calls use `<Conference record="record-from-start">` which records MONO (all parties mixed into one channel) → every sentence has the same channel → everything gets ONE label (DJ saw all "Customer"). OUTBOUND already uses `record="record-from-answer-dual"` (dual channel) so those label right. FIX = enable dual-channel for conference recordings on DJ's Twilio acct: **Console → Voice → Recordings → Settings → "Dual-channel Recording for Conference" → Enable**. Dual-channel conf recording puts the FIRST participant to join (= the inbound caller) on channel 1 and everyone else (DJ's bridged leg) on channel 2 — which matches the existing `channel1=Customer / else=Dan` mapping, so no code change needed IF VI reports channels as 1/2. ⚠ VERIFY channel numbering on the first real dual-channel inbound transcript (VI may 0-index → then flip the mapping).
