How the Saunders Printing (company_id=3) HOF invoice flow actually behaves (verified 2026-06-24, PO 044167 / invoice 200239):

**SA 1335 "Saunders: Email Invoice to HOF" = a REAL customer send, not a preview.** The printing-tracker green **Send Invoice** button → `POST /printing/api/jobs/{id}/send-invoice` → runs SA 1335, which: posts the draft, renders the PDF, emails it to `bhatton@baseballhall.org, retailinvoices@baseballhall.org` (NBHOF AP) with a tracking pixel, AND sends a silent `[COPY]` to windowandsolarcare@gmail.com, then marks the `invoice_sent` step. DJ had assumed "only a preview goes to me first" — NOT true; it hits the customer immediately. The green "NBHOF opened the invoice email" badge is that real customer open (open-tracking pixel `/printing/track/open`).

**Preview-to-Me (added 2026-06-24):** new `POST /printing/api/jobs/{id}/preview-invoice` (jobs.py) renders the CURRENT invoice via SA 1336 and emails it to DJ ONLY (`[PREVIEW — NOT SENT]` subject), does NOT post, does NOT email NBHOF, does NOT mark sent. Frontend `previewBtn` ("📩 Preview to Me") shows when `!invSent && shipped && odoo_invoice_id`. Real-send confirm text strengthened to make the distinction obvious.

**View Invoice staleness was browser cache, not Odoo.** `GET /printing/api/jobs/{id}/invoice.pdf` → SA 1336 re-renders fresh every time (it `unlink`s its prior `Invoice_{name}.pdf` attachment and recreates). The render is always current. The stale PDF DJ saw was the **browser/CDN caching** the response at the fixed URL. Fix: added `Cache-Control: no-store, no-cache, must-revalidate` + `Pragma`/`Expires` to `_serve_attachment` in jobs.py — covers View Invoice / View PO / Zoo Invoice. (Pointing at Google Drive would NOT have helped; the Drive copy comes from the same SA-1336 render.)

**$0-card guard (added 2026-06-24, watcher.py `_create_odoo_invoice`):** `_ensure_product` auto-creates a MISSING product at $0.228, but a product that already EXISTS in Odoo at `list_price=0` still bills $0 and slipped through. Guard collects any card pricing to $0, then after invoice create calls `_notify_dj` + `message_post` on the move so it's caught before sending.

**Invoice format note:** newer invoices bill ONE LINE PER CARD at the product price (e.g. $0.228) + a Freight line, no separate banding line (banding baked into product price). Older invoices (≤200238) used a single consolidated card line + separate Banding + Freight. PO total = `qty × PO Cost`; the PO's "PO Price" column (e.g. 0.99) is HOF's own retail price, irrelevant to what Saunders bills.

**NBHOF card-back design/art fee (agreed in email, 2026-05/06):** Saunders' STANDARD rate for developing a new card back = **$45.00 per back**; for the PO 044167 photo-postcard order DJ reduced it to **$25.00 per card back** (volume) and Ben Hatton agreed in writing ("the art fee for the back of the postcards is fine"). This is a SEPARATE line from the $0.228/unit print price. DJ forgot it on the first invoice 200239 → corrected 2026-06-26: reset posted invoice to draft (`button_draft`), added line "New Card Back Design Fee (21 @ $25.00)" = $525, re-dated to send-day, `action_post`. New total **$5,717.60** (was $5,192.60). GOTCHA: `button_draft`/`action_post` return None → XML-RPC throws "cannot marshal None" on the RESPONSE but the action DID run — wrap in try/except and verify state after. To edit a posted invoice: button_draft → write invoice_line_ids `(0,0,{...})` → action_post.

**DELIVERABILITY ISSUE (2026-06-26):** Ben Hatton emailed that he NEVER received invoice 200239 even though SA 1335 reported it sent to bhatton@+retailinvoices@baseballhall.org on 6/24 and the open-pixel fired (someone opened it — likely retailinvoices/accounting, or it hit spam). Odoo mail.mail showed state='sent' (no bounce) → non-delivery is receiver-side filtering, NOT an Odoo failure. So "is the invoicing email going out correctly?" = it leaves Odoo fine but may not LAND in the recipient's primary inbox. Possible real fix if it recurs = SPF/DKIM/DMARC for scenicartprint.com sending domain. The 6/26 reply to Ben (Gmail draft, DJ sends from dan@scenicartprint.com) asks accounting to confirm they have the corrected $5,717.60 copy.

**Dates (verified 2026-06-24):** invoice is dated the DAY IT'S SENT. `_create_odoo_invoice` leaves `invoice_date` blank on the draft; `send_invoice` writes `invoice_date=today` right before posting (backstop) and SA 1335 `action_post()` sets it on confirm; Net 30 → due = +30 days. Live 200239: invoice_date 2026-06-24, due 2026-07-24.

**Drive overwrite (verified 2026-06-24):** draft invoice PDF is filed to the `NBHOF PO {num}` Drive folder at PO-RECEIPT (watcher.py check_hof_emails ~L499) as `Invoice {num}.pdf`; `send_invoice` re-files the POSTED (non-draft) render under the SAME name; `drive_filer._upload_pdf` deletes any same-name file before upload = idempotent overwrite, one copy. Confirmed by downloading the live Drive file for 044167 + extracting text: title "Invoice 200239" (NO "Draft"), $5,192.60. FIXED 2026-06-24 (commit d052f0f): send_invoice no longer swallows a failed re-file — it captures the drive_filer error (or render failure) and emails DJ "⚠️ Invoice {n} sent to NBHOF but the Drive copy was NOT updated … tap File to Drive". Previously `try/except: pass` + the weekly-rotating Google OAuth token meant a dead token at send time silently left the DRAFT on Drive. NBHOF Drive root folder id `1wLCboY1FcXIYLF7_HBSc9VVI4WlO9qZh`. Note: two renders of the same posted invoice are SAME byte size but different md5 (Odoo embeds a fresh timestamp/ID) — size match ≈ same content, md5 mismatch is normal.

**FREIGHT IS ADDED AT INVOICE CREATION — NEVER defer it to "ship time" or "add at the end" (DJ rule, reaffirmed 2026-07-01).** Freight is FULLY KNOWN on day one: it's derived from a fixed table by total card qty, so the Freight line goes on the invoice the moment it generates. This is how the code is written (`printing_watcher.py` `_calc_freight` / `_create_odoo_invoice` add the Freight line in the same `create`) and it has ALWAYS been the agreed behavior. **Mistake to never repeat:** in the 2026-07-01 PO 044303 build I created the card + design-fee lines but LEFT FREIGHT OFF, wrongly reasoning "freight is added at ship time when the cost is known." Wrong — DJ had to correct it and I re-added it. If you're hand-building an NBHOF invoice, include Freight from the start. FREIGHT_TABLE (per 1,000 cards, linear interpolation between points): `1→22.27, 2→44.50, 3→66.80, 4→85.85, 9→187, 12→249, 15→307, 18→355.50, 20→385, 25→483, 30→562.50, 32→592.85`. `k = total_qty/1000`; clamp below 1k / above 32k. Verified: 21k → 404.60 (matches invoice 200239); 16k → 323.17 (PO 044303). **WHERE THE FREIGHT TABLE LIVES (to change it, e.g. a 5% raise):** it is HARDCODED as the `FREIGHT_TABLE` Python dict — NOT a document, spreadsheet, or Odoo record. Live/deployed file = `routers/printing/watcher.py` in the saunders-render-app repo (local clone `C:\Users\dj\wsc-repo\routers\printing\watcher.py`, dict at ~lines 36–40). To adjust pricing, edit the twelve dollar values in the dict and push; `_calc_freight` just interpolates whatever values are there, so the logic never changes. ⚠️ STRAY DEAD COPIES exist (`C:\Users\dj\printing_watcher.py` and `.../Migration to Odoo/1_Production_Code/printing_watcher.py`) — the ONLY one that runs is the wsc-repo copy; edit that one and ignore the strays. Design fee is a separate line ("New Card Back Design Fee (N card backs @ $25.00)", qty=N, $25, acct 266, no tax); $25/back was the volume rate for these postcards ($45 is the standard rate).

**Odoo quirk:** `account.move.line` `search_read` by `move_id` returns 0 under XML-RPC because of the multi-company record rule (active company = W&SC/1, lines are company 3). Read lines via the move's `invoice_line_ids` then `read` those ids instead.
