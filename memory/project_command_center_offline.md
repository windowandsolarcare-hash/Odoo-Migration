**Command Center (`/owner/command-center`, schedule_hub.html) offline + refresh model** — DJ relies on this in the field with frequent no-signal; treat offline correctness as a hard requirement here. Built/hardened 2026-06-29:

- **★ SW caching strategy (auth.py `_SW_JS`, fixed 2026-06-30):** navigations = network-first (fresh HTML); `/static/*.js` and `*.css` = NETWORK-FIRST (`var _code=/\.(js|css)$/i...`; `if(_code) return netP||cached`) so CODE changes (e.g. a redeployed ql_panel.js) show IMMEDIATELY when online instead of one launch late; other `/static` (images/fonts) = stale-while-revalidate (instant). Before this, SWR on JS caused "I don't see the new one" until a 2nd launch (hit on the ql_panel redesign). NOTE: changing `_SW_JS` itself still needs one full app close/reopen for the browser to swap to the new worker (skipWaiting+claim), then the new logic applies. Don't tell DJ "reopen" for every change anymore — only code in `_SW_JS` needs it now.
- **★ SW UPDATE = needs a FULL APP KILL, not log-off/in (2026-06-30):** DJ logging off and back on does NOT swap the service worker — the webview + old SW stay alive, so it keeps serving stale cached assets (he was stuck on the OLD ql_panel.js icon grid even after the labeled redesign deployed). Only a full swipe-close from the recent-apps list kills the webview so the browser fetches/activates the new `/sw.js`. STOP telling DJ "log off/in" or even "reopen" for code changes — say "fully swipe-close the app from recents, then reopen." Mitigations now in place: (1) SW cache bumped `wsc-shell-v1`→`v2` (activate purges ALL old caches); (2) `controllerchange` auto-reload added to index.html/myday.html/schedule_hub.html SW registration (`var _swR; addEventListener('controllerchange',()=>{if(_swR)return;_swR=true;location.reload()})`) so once the new SW claims, the page refreshes itself; (3) network-first for `/static/*.js|*.css` (see below). With these, future SW/code updates self-apply on a normal open — but the FIRST swap to the v2/controllerchange SW still needs one full app kill.
- **Page shell offline** = the service worker in `routers/auth.py` `_SW_JS` (network-first nav, cache fallback). See [[project_navigate_gps_first]] note / the sw.js work.
- **Data offline** = `cjson(url, keyOverride)` (IndexedDB store `wsc_cc`/`kv`). Returns the on-device cached copy INSTANTLY and never awaits the network when a cache exists — the network fetch (`_fetchJsonTimeout`, 8s) runs in the background and its errors are swallowed (`net.catch(()=>{})`). So an offline refresh CANNOT block or blank the screen; it re-renders the last saved schedule. Only a first-ever load with no cache returns `{}`.
- **Refresh** = ↺ header button `refreshCC(true)` + auto on return: `pageshow` (bfcache) + `visibilitychange`. CC is restored from bfcache when you tap back from a job panel and does NOT re-fetch on its own, so a Sync (e.g. job-type change) looked stale — refreshCC clears the in-memory `DATA.need/DATA.on/_calCache` and re-runs `loadNeed()/show(CUR)`, which re-read from IndexedDB (cache-first) then background-revalidate. Auto-refresh is throttled to 5s; manual ignores throttle. Clearing in-memory caches does NOT lose offline data (IndexedDB is the persistent layer).
- **★ Stable-key offline net (the date-rollover fix):** `calendar_jobs` URLs embed today's date (`isoPlus(-14)..+21` for On-schedule, `-90..today` for Needs). Without help, a NEW day = new URL = new cache key = MISS = empty list when offline. Fix: pass a stable `keyOverride` — `'cal:on'` and `'cal:need'` — so yesterday's saved payload (already spans ~3 weeks ahead, includes today) is found and rendered offline until signal returns. `scheduled_sos` calls have no date param so they were already stable. loadCalMonth (month browsing) intentionally left URL-keyed.
- **Field guarantee to tell DJ:** open the schedule once where there's signal (even briefly) → that view is saved and carries through dead zones; with the stable-key net, even a brand-new day with zero signal falls back to the last saved schedule instead of empty.

- **Break + End Day bar** ported from Field Assistant (mirrors its `#break-bar`): shares the same endpoints `/owner/api/payroll/{status,break,clockout_crew}` and the SAME localStorage keys (`wsc_emp_id`, `wsc_break`, `wsc_crew_today`, `wsc_pending_clockout`) so break/clock state stays in sync across both pages. Employee id sourced from `localStorage.wsc_emp_id` (set when DJ clocks in via Field Assistant); bar only shows while clocked in. End Day saves intent to localStorage before the fetch and drains on `online`/load (offline-safe).

- **Job-detail header date+time (2026-06-29):** the open-job header (`#ap-so` line) is the ONLY place the scheduled date/time shows. CC-opened jobs go through `openJobById`→`/api/so_history`, which returned `'date'` (date only) — no time — so the header showed a bare `2026-06-30`. FIX: so_history now also returns `'time_utc'` (`date_order[11:16]`); openJobById sets `time_utc` on the job; new `_apHeaderWhen(job)` renders "weekday Mon D · h:mm AM" (date from `date_raw`, time from `time_utc`→`toPT`; if a time but no date → today). `.ap-so`/`.ap-sched` now `flex-wrap:wrap` (+`.ap-time` no longer `nowrap`) so the longer string doesn't tuck under the Back/Schedule button.
