**THE BUG (DJ navigated to wrong address, Meredith Wilson, 2026-06-26):** a customer with TWO properties had the right address in Workiz but the WRONG one in Odoo. Field-app navigation uses the property `street` field; the corrupted property's `street` pointed to the customer's OTHER property.

**ROOT CAUSE = Odoo's built-in address inheritance.** A child res.partner with `type='contact'` (the DEFAULT) auto-syncs its address (street/city/zip) with its parent (commercial partner) AND all 'contact'-type siblings. So every property of a customer is chained to ONE shared street — whichever job was processed LAST overwrites them all. Proven: writing street to ONE property instantly cascaded to the sibling property + the parent contact (synchronous, same RPC). The `name` field is per-property and DOESN'T sync (so the display looks right), but `street` (what navigation uses) gets overwritten. **FIX: property records must be `type='delivery'` (or 'other') = an INDEPENDENT address that does NOT sync.** Property identity is by `x_studio_x_studio_record_category='Property'`, NOT type, so changing type is safe (don't filter properties by type — CLAUDE.md already warns this).

**CULPRIT path = `new_job.py` `api_intake_create_property`** (the New Order intake DJ books through) created properties WITHOUT `type` → defaulted to 'contact'. FIXED 2026-06-26 (commit 2cc6834) → now sets `type='delivery'`. Phase 3's `create_property` (zapier_phase3) was ALREADY correct (`type='other'`). Watch quotes.py walk-up / brain.py / any other res.partner property create — they must set type too.

**NOT a Workiz problem — it's pure Odoo, persists post-Workiz (DJ asked 2026-06-26).** The address inheritance is built-in Odoo behavior, and the culprit creation path (new_job.py New Order intake) is Odoo-native (Render→Odoo, no Workiz). A multi-property customer booked entirely in Odoo still hits it unless type='delivery'. Workiz was only a frequent TRIGGER (every Phase 3/4 job sync writes property addresses → more chances to fire the cascade); removing Workiz reduces trigger frequency but does NOT fix the latent flaw. STRATEGIC POINT for the Workiz exit: much of what we keep fixing (this, phantom last_property_visit dates [[project_reeng_duedate_audit_and_declutter]] note, duplicate property records like Donna's Court/Ct) is **Odoo-side DATA INTEGRITY** that does NOT disappear when Workiz leaves — Workiz's exit only simplifies the SYNC PLUMBING (Phase 3/4/5/6, trigger jobs, two-system reconciliation). Don't assume "post-Workiz" auto-solves data-model issues.

**Navigation reads `street`** (not name). The rebind safety-net `_rebind_so_to_matching_property_if_needed` (phase4) couldn't help — it searches for a property whose street matches the job address, but the cascade had corrupted every property's street, so no match. **How to apply / prevent:** any code creating a Property res.partner MUST set `type='delivery'`. To find recurrence: `res.partner` where record_category='Property' and type='contact'.
