## ★★ CANONICAL CRM LIFECYCLE (DJ's complete loop, articulated 2026-07-06) ★★
**Universe = every customer with a DONE job / invoice in their sales history.** (No sales history ever = a LEAD, tracked SEPARATELY, not in this loop. DJ wants leads identified separately.) Every "done-business" customer sits in EXACTLY ONE of three states at any time, and they flow between them:

1. **MAINTENANCE** — committed to a recurring plan. Cycles on their frequency. Already works; leave it. Never leaves this state unless they lapse.
2. **RE-ENGAGEMENT** — active/current customer who did NOT commit to maintenance (on-request). A BOUNDED 2-touch sequence measured from LAST SERVICE, then hands off:
   - **6 months** after last service → re-engagement message #1.
   - **8 months** (2 months later) → message #2 (a different/second message).
   - then **sit 4 months** → at **12 months** (1 year since last seen) with no return → **converts INTO the Reactivation campaign.**
   - (NOT an infinite loop — 2 touches then hand off. If they book at any point → back to active; recommit to maintenance → Maintenance, else → re-engagement clock restarts from the new service date.)
3. **REACTIVATION** — NOT active: no business in 12+ months. Runs as the reactivation campaign with its OWN message type (different from re-engagement). Reaches out → **cooldown (~6–8 months? DJ unsure — "something like that"; earlier I found the code default = 365 days / 12mo)** → picked up again the next cycle with the reactivation campaign. Cycles ~annually until they return or are set inactive/DNC.

**Reconciles to the customer base:** (verified counts 2026-07-06) active-within-12mo **250** (= Maintenance + Re-engagement, split needs deriving) + lapsed >12mo **292** (= Reactivation) = **542 done-business customers**; + **220 never-served (LEADS, separate)** = 762 non-property contacts. 21 are Do-Not-Contact (orthogonal exclude). ★ The Maintenance-vs-Re-engagement split CANNOT be read from `x_studio_x_type_of_service` (≈all 'Unknown' on contacts) — must derive from behavior (has a recurring frequency/cadence = maintenance; served but no schedule = re-engagement).

**★ BUILD DELTAS this model implies (NOT yet built):**
- Re-engagement is a **2-touch bounded sequence (6mo/8mo) then convert to reactivation at 12mo** — NOT the current infinite 60-day resurface loop. Current `WAIT_ON_REPLY_DAYS=60` covers the 6mo→8mo gap (touch 2), but after touch 2 it must **convert to a reactivation lead at 12mo**, not resurface again.
- Reactivation cadence number is UNSETTLED (DJ floated 6–8 months AND "next year"; code cooldown = 365d). NAIL DOWN before building.
- Need a clean **state classifier** (by sales history + last-service date + frequency) that assigns each done-business customer to exactly one of the 3 states — this is the real reconciliation engine (ties into Customer Analytics).

- **NO-REPLY** (wait_until passes) → resurfaces as attempt 2.
- **DEFERRED / not-ready** (new one-tap button: log reason to chatter, set deadline = today + preset) → drops off till then. Closes current loop + opens next in one move.
- **BOOKED** → existing automation id 9 closes it; Phase 5 makes the next cycle's task.
